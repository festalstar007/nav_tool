# nav_tool 设计文档

状态：最小 MVP 已实现并启动，优先通过本地浏览器验看效果；实现和验证结果见 `implementation.md`。

## 1. 背景与目标

用户原先喜欢 Edge 的书签同步体验，转到 Linux 后，希望将书签统一放在自己的 VPS 上管理。只需记住一个主页即可访问，不要求跨浏览器同步，也不依赖浏览器扩展。

核心目标是一个克制的个人导航工具：左侧分类树，右侧尽可能密集地展示书签名称和图标，方便浏览、定位和打开。重视开源、简洁、低资源占用和后续自行修改。

现有方案的参考：linkding 的 MIT 协议和简洁定位、Linkwarden 的层级分类、WebStack 的分类导航布局。最终决定新建自己的 `nav_tool` 工程，不直接把这些产品的完整功能集搬进来。

工程路径：`/home/fstar/project/nav_tool`，与 `code_helper` 同级。

开源许可偏好：MIT；正式发布前补齐项目 LICENSE，并检查依赖及素材许可。

最新交付范围：先验看登录、层级分类、紧凑书签网格、搜索、导入与编辑排序。备份已有基础实现，但不再为预览阶段扩展功能；异地存储保持延后。

## 2. 已确认的范围

### 页面与管理

- 桌面端左侧展示可折叠的分类与子分类，点击后定位或筛选右侧书签；具体交互实施时确定。
- 右侧使用紧凑多列网格，每项优先仅展示小图标和名称，减少大卡片、缩略图和长描述占用的空间。
- 提供全局书签搜索；描述或备注可通过悬停、详情或编辑界面查看。
- 提供分类和书签的新增、修改、删除与排序，以及单管理员登录。
- 所有设备访问同一服务端数据。浏览器本地存储不作为书签的唯一数据源。

### 导入

- 至少支持一种常用浏览器的书签导入，优先支持 Edge/Chrome 导出的 Netscape HTML 格式。
- 尽可能保留文件夹层级、书签名、网址和原有顺序。
- 导入前提供基本结果确认，并明确重复网址处理规则，避免静默覆盖。
- Firefox 等其他浏览器兼容性按实际导入验证决定，不提前承诺。
- 导出不是第一版必需功能；完整数据保护由备份机制承担。

### 不纳入第一版

- 跨浏览器原生书签栏双向同步、浏览器扩展。
- AI 标签与摘要、全文网页存档、截图和 PDF 抓取、稍后阅读系统。
- 团队权限体系、公告、监控仪表盘和动态卡片。
- 复杂的逐文件校验清单、周期性自动恢复演练及多层验证状态。

## 3. 技术方案

| 部分 | 选择 |
| --- | --- |
| 后端 | Go，优先标准库 `net/http` |
| 数据访问 | SQLite + `database/sql`，驱动待实施时选择 |
| 前端 | React + TypeScript + Vite |
| 布局样式 | 普通 CSS + CSS Grid |
| 前端状态 | 优先 React 自带状态管理 |
| 服务方式 | Go 同时提供 API 与构建后的静态前端 |
| 公网入口 | Caddy，负责 HTTPS 与反向代理 |
| 进程运行 | 本机采用 systemd 用户服务 `nav-tool.service`，启用 linger；Docker 为备用部署方案 |

前端在浏览器运行，Node.js 仅用于开发和构建。可以在开发机生成前端文件并编译 Go，避免弱 VPS 承担构建开销。不需要 Next.js、服务端渲染、Redis 或独立数据库服务。

资源控制重点是图标抓取、导入和备份：限制并发与文件大小，设置超时，避免无限队列和反复请求。实际内存占用上线前测量，不预设未经验证的资源数字。

## 4. 数据与文件组织

建议持久化目录：

```text
data/
├── nav.db        # 分类、书签、管理员、应用设置
└── icons/        # 缓存及上传的图标
```

运行中 SQLite 可能产生 WAL 等辅助文件，由 SQLite 管理，不手工删除。

概念数据模型：

- 分类：稳定 ID、父分类 ID、名称、排序、创建和修改时间。
- 书签：稳定 ID、所属分类 ID、名称、网址、图标引用、备注、排序、创建和修改时间。
- 管理员：登录标识及安全的密码哈希，不存明文密码。
- 设置：界面和备份等应用配置；存储凭据等敏感信息采用受限配置管理。

分类深度上限、同一书签是否允许跨分类出现、网址规范化与去重规则，实施前明确。禁止形成分类循环；删除含子分类或书签的分类时需要明确处理规则。

图标不存入数据库。可重新抓取的缓存图标和用户上传图标统一纳入备份；缺失图标使用默认占位，不影响打开书签。

为以后扩展同步保留稳定 ID 和修改时间。真正实施增量同步时，再设计删除记录与冲突处理。不要通过直接同步运行中的 SQLite 文件实现跨设备同步。

## 5. 基本后台备份

第一版仅实现本地备份。异地备份后续再考虑，只预留内部存储接口，不实现 WebDAV、S3 等适配，也不展示未实现的异地配置控件。

### 备份内容

- SQLite 一致性快照。
- `icons/` 图标目录。
- 恢复所需的应用配置；敏感配置应受访问控制保护，不在界面或日志中展示。
- 简单的备份说明，记录备份时间、应用版本和数据库结构版本，方便恢复判断。

程序与前端构建产物可重新部署，不必放入每份数据备份。

### 备份流程

1. 后台定时触发，也提供“立即备份”。
2. 在临时目录中生成 SQLite 一致性快照，使用 SQLite 在线备份 API 或等效的一致性机制；不直接复制运行中的 `nav.db`。
3. 复制图标与必要配置。为保持图标与数据库对应，备份取快照及复制期间短暂阻止相关修改，浏览访问继续。
4. 对数据库快照运行 `PRAGMA integrity_check`，确认返回 `ok`；失败则终止并保留错误状态。
5. 将数据打包为单个归档文件，写入本地备份目录，确认文件成功关闭并落盘；未完成的临时文件不计为有效备份。
6. 全部完成后记录成功时间；成功后再按保留策略清理过期备份，失败不得删除已有的有效备份。
7. 清理本次临时文件，控制本机备份空间占用。

### 验证与恢复

采用基本步骤即可：每次执行数据库完整性检查、确认归档成功保存、保留多个历史版本。保存成功不等同于已经实际恢复验证。

首次部署后实际恢复一次，确认管理员登录、分类、书签和图标正常。数据库结构或备份逻辑发生重大变化后再验证恢复。暂不做逐文件 SHA-256 清单或每周自动恢复演练。

恢复时停止应用或阻止写入，恢复数据库、图标及配置，再启动匹配版本的应用。恢复到干净的数据目录，避免旧 WAL 文件与恢复的数据库混用。

### 后台显示

- 是否启用定时备份、备份周期、本地备份位置和保留策略。
- 最近一次备份时间、成功或失败状态、简明失败原因。
- “立即备份”入口；恢复入口的具体形式待实施确定，覆盖当前数据前必须明确确认。

周期与保留数量尚未确定。每天一次、保留多个历史版本可以作为默认候选。

### 异地存储扩展接口

备份生成与存储职责分开：备份模块负责快照、检查和打包，存储接口负责保存归档、列出已有备份和删除过期备份。第一版提供本地文件系统实现，后续可增加 WebDAV、S3 或其他异地存储实现。无需为此暴露公网 API 或提前配置异地凭据。

## 6. 部署与安全

已确认的部署信息：用户本机已有 Caddy，导航主页使用 `https://nav.345001.xyz`。用户稍后自行处理域名的外网配置；DNS 解析与公网可达性尚未验证。该域名作为后续正式访问入口，不表示当前应用已经上线。

后续部署时先检查现有 Caddy 配置，在保留其他站点的前提下，为该域名添加到 nav_tool 本机上游的路由。应用监听地址和端口待实施时确定。本次仅记录部署方式，不修改 Caddy、DNS、TLS 或防火墙配置。

部署前确认实际主机服务，不把环境约定当成事实。默认考虑 Caddy 为公网入口、UFW 为主机防火墙，并保留必要 SSH 访问。

Go 应用通过回环地址或隔离容器网络接受 Caddy 代理，不单独向公网开放应用端口。数据和备份目录不映射为公开静态资源。静态前端与 API 的认证、读取范围保持一致；个人书签默认按私有数据设计。

图标获取只接受允许的 URL 类型，限制响应大小、重定向和访问目标，防止公开接口被用于访问主机内网或元数据服务。导入内容按文本渲染，避免名称、备注或恶意网址形成脚本执行。

## 8. 第一版验收标准

以下为待实现的验收清单，勾选需有实际验证结果支持。

### 导航与日常管理

- [ ] 登录后可查看左侧分类树，展开和折叠子分类，点击分类能够正确展示或定位对应书签。
- [ ] 右侧以紧凑多列网格展示小图标与书签名，不默认展开长描述或大缩略图；常用桌面窗口下无横向溢出，长名称可查看完整内容。
- [ ] 可打开书签；图标缺失或加载失败时显示占位图标，不影响名称和链接使用。
- [ ] 全局搜索至少匹配书签名称和网址，能够跨分类查找；清空搜索后可返回正常分类浏览。
- [ ] 可新增、修改、删除和排序分类与书签，也可调整书签所属分类；刷新页面或重启服务后修改仍然保留。
- [ ] 分类移动不会产生循环；删除含子分类或书签的分类时按明确规则处理，并在破坏性操作前提示确认。
- [ ] 换一台设备登录同一服务后可访问同一份数据，无需重新导入。
- [ ] 未登录时不能读取私有书签或执行管理操作，退出登录后受保护接口不可继续使用。
- [ ] 页面遵循 `AGENTS.md` 中的 UI 约定：状态与操作清楚，文案简短，不堆砌说明和实现细节。

### 书签导入

- [ ] 至少使用一份真实 Edge 导出的 HTML 文件完成导入，包含中文名称、多个文件夹、子文件夹和多个链接。
- [ ] 导入后分类层级、名称和网址正确，支持范围内保留原有顺序；任何层级转换或不支持项在确认时简要提示，不静默丢弃。
- [ ] 导入前能查看基本结果并确认执行；取消时不写入数据。
- [ ] 重复导入同一文件时，按确定的规则处理重复项，并显示新增、跳过或失败数量，不静默覆盖已有修改。
- [ ] 无效或超限文件被明确拒绝，已有数据保持有效；导入内容不能作为脚本执行。

### 后台备份与恢复

- [ ] 可配置并执行定时备份，也可手动触发；归档包含一致性数据库快照、独立图标目录和必要配置。
- [ ] 数据库快照的 `PRAGMA integrity_check` 返回 `ok` 后才继续打包保存；检查失败时记录失败，不标记成功。
- [ ] 归档成功保存到本地备份目录；保存失败时显示简明原因，且不清理已有有效备份。
- [ ] 备份生成与存储通过内部接口分离，第一版使用本地实现，后续可扩展异地存储，无需重写快照和打包流程。
- [ ] 按确定的保留策略保存多个历史版本，并在新备份成功后清理过期版本和本次临时文件。
- [ ] 后台可查看最近一次备份时间和成功或失败状态；界面和日志不泄露存储凭据。
- [ ] 使用一份本地备份，在独立目录实际恢复一次；确认可登录，分类层级、书签数量、网址和图标与备份时一致，不覆盖正在使用的数据。

### 运行与部署

- [ ] 构建后的前端和 Go 服务可以独立运行，生产环境无需启动 Node.js 开发服务器或独立数据库服务。
- [ ] 数据目录持久化，应用重启后数据和图标不丢失；记录空闲、导入和备份期间的实际资源占用，结合 VPS 可用资源评估。
- [ ] 通过 Caddy HTTPS 访问，应用端口不绕过 Caddy 暴露公网，数据库、图标源目录和备份归档不能被匿名下载；保留必要 SSH 管理访问。
